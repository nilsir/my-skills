# 双文档合并通知模板

同一需求的测试交接与前端联调一起发布到企微时，默认使用本模板，在同一个群发一条合并通知。分别发布两份正文，在通知里保留两个独立的文档链接。用户另有明确安排时按用户要求执行。

## 排版与内容

先读本次前端联调和测试交接两份正文。从联调文档提取影响页面接入的接口变化，从测试文档提取需要执行的验收场景。两篇提到同一变化时，前端写如何接，测试写如何判定通过。环境、版本、共用测试数据和部署依赖只写一次。两份正文对字段、版本或状态描述不一致时，先对照代码或环境核实，未核实处标明“待确认”。

- **项目与版本**逐项目列出源分支、目标分支和本次交付内容。附已核实的 MR、提交或流水线链接。仅复用现有接口的项目标明“无需发版”，参与联调但分支未知的标明“分支待补”。
- **部署与验收步骤**按目标环境和实际依赖排序。每步写明执行对象、版本或变更、验收动作及预期结果。SQL、配置等前置操作标明在哪个环境已执行、哪个环境待执行。最后写清业务放行条件。
- **Mall API 和 Mall Admin 是两个独立部署项。** 两者都涉及时分别写一行，各列发布版本和本服务的验收步骤；即使共用分支或提交，也要分别核对运行版本。只涉及其中一个时，只列该服务。下面的示例按本次需求增删、排序后再发送。
- **前端联调重点**写到能动手接入的程度。选择影响最大的入口，给出页面动作、请求方法和路径、关键参数或返回字段，以及页面如何处理。按需补充旧数据兼容、空态或错误回显，完整 JSON 示例留在联调文档。
- **测试验收重点**写成可以执行和判定的用例。交代测试数据、操作和可观察的预期结果，优先覆盖主流程、最容易出错的边界及受影响的旧功能。标明后端在哪个环境自验过、哪些仍待页面或端到端验收。
- 两组重点各列 1—3 条，简短通知也保留两组条目和两个独立链接。部署步骤里的验收只写该服务就绪的检查，完整业务场景放在测试重点。

```markdown
**📣 需求交付｜〈需求名称〉**

〈一句话说明谁在哪个页面做什么，以及本次有什么变化〉

**📦 项目与版本**
- **〈项目名〉**　〈源分支〉 → 〈目标分支〉。〈本次交付内容、当前状态及关联 TAPD、MR 或流水线链接〉
- **〈联调项目名〉**　〈源分支 → 目标分支，或分支待补〉。〈需要配合发布的页面或功能〉
- **联调环境**　〈环境或入口、实际已部署版本、当前可验证范围。如需特定权限或测试数据，在这里注明，不填凭据〉

**🚀 部署与验收步骤｜〈目标环境〉**
1. **〈前置依赖，如有〉**　〈SQL、配置或定时任务的实际变更，各环境执行状态、待执行动作与验证方法〉
2. **Mall API**　部署〈版本〉。验收〈调用受影响的读取接口，核对响应中的关键字段及预期值〉。
3. **Mall Admin**　部署〈版本〉。验收〈在后台执行受影响的操作，重新读取并核对结果〉。
4. **〈联调项目，如有〉**　〈切换版本或接入接口，在目标页面验证完整业务流程〉。
**放行条件**　〈哪些服务版本和关键场景验收通过后，可以启用功能或发布首条业务数据〉。

**📚 交接文档**
〈原样插入解析器返回的 mention_markdown〉
- 🧪 [测试交接与验收清单]({document_url})
- 🔌 [前端接口与联调说明](〈已发布的前端文档真实链接〉)

**🔌 前端联调重点**
1. **〈页面动作〉**　调用〈方法及路径〉，传〈关键参数〉，根据〈返回字段或状态〉展示〈页面结果〉。
2. **〈兼容或异常场景〉**　遇到〈旧数据缺字段、空结果或请求失败等实际情况〉时，页面应〈回退、提示或定位方式〉。

**🧪 测试验收重点**
1. **主流程**　用〈测试数据〉执行〈关键操作〉，应看到〈页面、接口或数据结果〉。
2. **边界与回归**　触发〈边界或失败条件〉，应〈具体表现〉。用〈既有数据或旧入口〉复核〈原有行为〉。

**已验**　〈环境、已验证的行为〉。**待验**　〈负责角色、端或链路、待验场景〉。
```

每次按[关联人员提醒规则](TAPD关联人员提醒.md)读取当前 TAPD 任务和相关子任务，核实前端、后端、测试分工。没有 TAPD 链接时先检索确认关联。将核实并匹配的企微 userid 去重，在同一条通知的两个正文链接前集中真实 @，每人一次。未匹配和按配置跳过的人员在交付结果中说明。

最终通知保留唯一 `{document_url}`，由 `group_notify.markdown_payload()` 替换为测试文档真实链接。前端链接先填入已发布的实际 URL。发送前核对两个文档链接、两组重点及同一条通知中的 TAPD @。完整内容含链接及 @ 不超过 4096 UTF-8 字节。超长时压缩摘要和条目措辞，保留两组重点、两个链接及提醒对象。

## 双文档发布与去重

现有单文档 `publish` 会自动通知，不能直接连续执行两次，也不要编造不存在的批量 CLI 参数。复用 `SharedPublisher` 的正文和共享目录能力，逐份发布时在本批内存配置中关闭自动通知，不修改用户长期群配置；两篇正文、权限和目录都核对成功后，再通过既有持久通知机制发送合并消息。若当前执行路径不能延迟单篇通知，先补齐这一能力，不能先发两条再解释。

- 同批登记两份正文的稳定键、实际 URL 和内容哈希，固定排序生成批次版本；同一需求的批次键保持稳定，任一正文的新版本均参与版本判断，不能只用第一篇的哈希去重。
- 只创建一个通知事件，包含两份文档键/版本及完整载荷。成功写入 `sending` 后才发送；两篇未全部核验成功不发，失败恢复沿用原文档和事件，不重复建正文。
- 同批内容未变且事件已 `sent`，不再通知；`sending/unknown` 只读回核对，不清状态、不自动重发。已知拒绝或尚未发送时，沿原事件处理，不换 ID 绕过防重。
- 仅更新模板或人员名单，不补发历史通知。用户明确要求修正已经发出的通知时，保留原 `sent` 记录，以独立修正事件关联原事件；现有发送工具不支持原地改消息时，说明将新增一条修正版。一次修正仍只发一条，不能把已发送事件改回待发送。
- TAPD 读取不等于回填或推进节点授权；按已授权的交付联动范围操作，不因补 @ 自动完成开发或测试节点。无真实关联不伪造对象。

发布后分别报告两篇文档、唯一通知事件和人员匹配结果。接口 `sent` 只表示已接受发送，不代表群成员已阅读或实际收到 @。
