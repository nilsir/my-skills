# 双文档合并通知模板

同一需求的测试交接与前端联调两份独立文档一起发布时，默认采用本模板，并只发一条通知；用户另有明确安排时遵从。两份正文和各自链接保留，不合并正文，也不把两套通知全文简单拼接。此规则不授权发布其他内容或补发历史通知。

## 排版与内容

便于手机阅读：一个标题、一句业务摘要，采用加粗分组、少量 emoji、短列表；每组通常 1—3 条，不使用表格，不堆叠长段落。保留测试与前端各自重点，共享依赖只写一次。分支、环境、自验、验收和部署状态按真实证据填写；接口字段全集、详细用例及 SQL 正文放在文档里。

```markdown
**📣 需求交付｜〈需求名称〉**

〈一句话说明业务变化〉

**📦 交付信息**
- 项目／分支：〈真实项目和分支〉
- 当前状态：〈开发自验、前端联调、测试验收、部署分别说明〉
- 关联需求：〈已核实 TAPD 链接；确无关联时省略〉
- 代码评审：〈实际 MR 链接；不适用时省略〉

**📚 交接文档**
〈原样插入解析器返回的 mention_markdown〉
- 🧪 [测试交接与验收清单]({document_url})
- 🔌 [前端接口与联调说明](〈已发布的前端文档真实链接〉)

**⚙️ 上线依赖**
- SQL／定时任务：〈已核实依赖；没有则写无〉
- 环境／配置：〈跨项目版本、开关、所需测试数据等〉

**🔌 前端联调重点**
1. 〈页面主流程与关键契约〉
2. 〈字段、状态、跳转或空态边界〉

**🧪 测试重点**
1. 〈核心正例与边界〉
2. 〈回归及尚待验收的关键项〉

**🚀 执行顺序**
1. 〈环境与依赖准备〉
2. 〈接入联调、测试验收及后续启用顺序〉
```

没有 TAPD 链接时，按技能入口先检索确认关联，再读取当前任务、直接父需求和同层子任务；不把缺链接等同于无关联。userid 去重后全部加入同一条通知，不用普通“@姓名”或 `@all`。未匹配和按配置跳过的人员在交付结果中说明，不在群中展示账号问题。正文入口前放真实 @，两份文档不能各 @ 一遍。

最终通知保留唯一 `{document_url}`，由 `group_notify.markdown_payload()` 替换为测试文档真实链接；前端链接先填入已发布的实际 URL。这只是兼容现有单链接替换函数，不代表只检查第一份文档。完整内容含链接及 @ 不超过 4096 UTF-8 字节；超长时缩短技术摘要，不删除文档入口或提醒对象。

## 双文档发布与去重

现有单文档 `publish` 会自动通知，不能直接连续执行两次，也不要编造不存在的批量 CLI 参数。复用 `SharedPublisher` 的正文和共享目录能力，逐份发布时在本批内存配置中关闭自动通知，不修改用户长期群配置；两篇正文、权限和目录都核对成功后，再通过既有持久通知机制发送合并消息。若当前执行路径不能延迟单篇通知，先补齐这一能力，不能先发两条再解释。

- 同批登记两份正文的稳定键、实际 URL 和内容哈希，固定排序生成批次版本；同一需求的批次键保持稳定，任一正文的新版本均参与版本判断，不能只用第一篇的哈希去重。
- 只创建一个通知事件，包含两份文档键/版本及完整载荷。成功写入 `sending` 后才发送；两篇未全部核验成功不发，失败恢复沿用原文档和事件，不重复建正文。
- 同批内容未变且事件已 `sent`，不再通知；`sending/unknown` 只读回核对，不清状态、不自动重发。已知拒绝或尚未发送时，沿原事件处理，不换 ID 绕过防重。
- 仅更新模板或人员名单，不补发历史通知。用户明确要求修正已经发出的通知时，保留原 `sent` 记录，以独立修正事件关联原事件；现有发送工具不支持原地改消息时，说明将新增一条修正版。一次修正仍只发一条，不能把已发送事件改回待发送。
- TAPD 读取不等于回填或推进节点授权；按已授权的交付联动范围操作，不因补 @ 自动完成开发或测试节点。无真实关联不伪造对象。

发布后分别报告两篇文档、唯一通知事件和人员匹配结果。接口 `sent` 只表示已接受发送，不代表群成员已阅读或实际收到 @。
