# CLAUDE.md 评分细则

## 通用评分规则

### N/A（不适用）维度

某些维度对特定项目类型确实无关时，可标记为 **N/A**，不计入总分，避免无理由扣分。

- **可 N/A 的维度**：架构上下文（结构极简的小项目）、安全与规则（无密钥 / 数据库 / 生产环境 / 敏感操作）、测试规范（无测试体系且非可测试代码项目，如纯文档 / 配置仓库）。
- **始终适用、不可 N/A**：简洁性、命令完整性、代码风格、行为约束、可读性。
- 标记 N/A 必须在报告中说明理由（如"纯静态站点，无后端与密钥"）。

### 总分折算

总分按**适用维度**折算为百分制，再据此评级（不要直接用原始 /80 判断）：

```
百分制 = 实得分总和 / 适用维度满分总和 × 100%
```

例：某项目架构、安全两维度标 N/A，则适用满分 = 60；实得 48 → 48 / 60 = 80% → 🟢 良好。

### 评级按百分制

所有评级一律以百分制对照文末「评级对照表」。有 N/A 时原始分上限低于 80，直接用原始分会误判。

## 维度一：简洁性（0–10 分）

| 分数 | 标准 |
|------|------|
| 9–10 | ≤ 100 行，无冗余，每条规则都有存在必要 |
| 7–8  | 100–200 行，偶有冗余但整体精炼 |
| 5–6  | 200–300 行，存在可删除的内容 |
| 3–4  | 300–500 行，大量内容可移至 skills |
| 0–2  | > 500 行，或充满无用套话 |

**检测点：**
- 数行数：`wc -l CLAUDE.md`
- 是否有大段架构说明（应移至 skills）
- 是否有只在特定任务才需要的内容
- 是否重复描述 Claude 本来就会的事

**完整性 gate：** 简洁性奖励的是"精炼"，不是"内容缺失"。若命令完整性、代码风格、测试规范、安全与规则中有 ≥ 2 项得分 ≤ 2（说明文件严重不完整），简洁性最高只给 5 分——文件短是因为没写，不应得高分。

---

## 维度二：命令完整性（0–10 分）

| 分数 | 标准 |
|------|------|
| 9–10 | 完整列出 build、test、lint、dev server 等所有常用命令 |
| 7–8  | 列出了主要命令（test/build），缺少 1–2 个常用命令 |
| 5–6  | 只有部分命令，或命令写得模糊 |
| 3–4  | 只提到"有测试"但没给命令 |
| 0–2  | 完全没有命令 |

**检测点：**
- 是否有 `## Commands` 或等价章节
- 是否覆盖：build、test（单测）、lint、type check、dev server
- 命令是否具体可执行（不是"运行测试"而是 `npm run test`）

> 去重说明：测试命令的"有无"在本维度计分。维度六只评测试**规范**，不因"缺测试命令"二次扣分。

---

## 维度三：代码风格（0–10 分）

| 分数 | 标准 |
|------|------|
| 9–10 | 明确指定语言规范、模块格式、命名约定、框架偏好 |
| 7–8  | 有基本规范，缺少 1–2 个关键约定 |
| 5–6  | 只有笼统描述（"写好代码"类） |
| 3–4  | 极少规范 |
| 0–2  | 无任何代码风格说明 |

**检测点：**
- 模块格式（ESM vs CommonJS / import 方式）
- TypeScript 配置（strict mode？）
- 命名风格（camelCase / snake_case？）
- 框架约定（React hooks、组件结构等）
- 是否有指向现有 pattern 文件的引用

---

## 维度四：架构上下文（0–10 分）

| 分数 | 标准 |
|------|------|
| 9–10 | 说明了关键目录结构、状态管理方案、核心依赖用途 |
| 7–8  | 覆盖了大部分，缺少个别关键模块 |
| 5–6  | 只有目录列表，没有说明用途 |
| 3–4  | 非常零散的架构说明 |
| 0–2  | 没有任何架构信息 |

**检测点（视项目规模调整预期）：**
- 状态管理在哪里（Zustand / Redux / Context？）
- API 请求如何处理（React Query / SWR？）
- 路由方案
- 关键 src/ 子目录的用途

**注意：** 结构极简、架构太简单无需说明的小项目，本维度应标 **N/A**（见「通用评分规则」），按折算不计入总分——不要既不打满分也不打 0 分。只有"项目有明显架构却没写清"才按上表扣分。

---

## 维度五：行为约束（0–10 分）

这是行为约束的核心维度之一。

| 分数 | 标准 |
|------|------|
| 9–10 | 明确包含全部四条行为约束原则或等价表述 |
| 7–8  | 包含 3 条原则 |
| 5–6  | 包含 2 条原则 |
| 3–4  | 包含 1 条原则，或表述过于模糊 |
| 0–2  | 没有任何行为约束 |

**四条必须检测的原则：**

1. **思考优先**：遇到歧义要问，不要假设；呈现多种方案；适时提出异议
   - 关键词：不假设、询问、澄清、呈现权衡、反驳

2. **简洁优先**：最少代码、不过度抽象、不添加未要求的功能
   - 关键词：最少代码、不过度设计、简洁、不添加未要求

3. **精准修改**：只改必须改的，不碰无关代码
   - 关键词：只改、不碰无关、不重构、精准、surgical

4. **目标驱动**：定义成功标准，循环验证
   - 关键词：测试先行、验证、成功标准、循环直到

## 维度六：测试规范（0–10 分）

| 分数 | 标准 |
|------|------|
| 9–10 | 说明测试框架、如何运行单个测试、覆盖率要求 |
| 7–8  | 有测试命令和框架说明 |
| 5–6  | 提到测试但缺少具体指引 |
| 3–4  | 只说"要写测试" |
| 0–2  | 完全没有测试相关内容 |

**检测点：**
- 使用什么测试框架（Jest / Vitest / pytest？）
- 如何运行单个测试文件（性能考虑）
- 新代码是否需要配套测试
- 是否有覆盖率要求

> 去重说明：与维度二的去重——测试命令的有无已在维度二计分。本维度只评测试**规范**（框架说明、单测运行方式、覆盖率、新代码配套测试要求），不因"缺测试命令"重复扣分。

---

## 维度七：安全与规则（0–10 分）

| 分数 | 标准 |
|------|------|
| 9–10 | 明确禁止项（不提交密钥）+ 项目特定约束 |
| 7–8  | 有安全禁令，缺少项目特定规则 |
| 5–6  | 只有非常笼统的安全说明 |
| 3–4  | 极少的硬性规则 |
| 0–2  | 完全没有约束性规则 |

**注意：** 无密钥 / 数据库 / 生产环境 / 敏感操作的项目（如纯算法库、静态站点），本维度应标 **N/A** 不计入，而非强行扣到 0–2。

**常见必要规则：**
- 永不提交 API 密钥、tokens、.env 内容
- 不直接修改生产数据库/配置
- 特定文件/目录的只读约束
- 依赖版本约束（不随意升级主版本）

---

## 维度八：可读性（0–10 分）

| 分数 | 标准 |
|------|------|
| 9–10 | 标题清晰、层级合理、人类和 AI 都能快速扫描 |
| 7–8  | 基本结构清晰，个别章节略乱 |
| 5–6  | 有章节但组织不佳 |
| 3–4  | 大段散文，无结构 |
| 0–2  | 完全无结构的文本墙 |

**检测点：**
- 是否有二级标题（`##`）分组
- 列表优于长段落
- 命令用代码块包裹
- 没有过度使用加粗（每个词都加粗 = 无重点）
